## Phase 1 — Repository account

### What this repository is

The repository is a VLM-based OCR/HTR pipeline for the Stefan Zweig estate held at the Literaturarchiv Salzburg, run as an experimental sub-project of Stefan Zweig Digital (`README.md:1-6`). Its stated methodological framing is that all code, pipeline architecture, frontend, and documentation were produced through the Promptotyping method with Claude Code, while the project lead acted as project manager and domain expert rather than as a hand-coding developer (`README.md:3-4`). The knowledge vault carries the same framing in its frontmatter (`knowledge/index.md:6-8`).

The repository holds three coupled artefacts: a Python transcription and export pipeline under `pipeline/`, a static single-page viewer under `docs/` that doubles as a local editorial workspace, and a Markdown research vault under `knowledge/` that documents data, method, and decisions. The result data lives under `results/{collection}/` and the built viewer data (`docs/catalog.json`, `docs/data/`) is committed for GitHub Pages.

### Corpus scale and nature

The corpus figures diverge across documents, and the divergence is itself informative. The README front matter states 2,107 digitised objects with 18,719 facsimile scans across four collections at roughly 23 GB (`README.md:6,23`). The knowledge vault gives a larger and later count of five collections, 2,486 physical backup objects, 20,318 images, and roughly 25.6 GB (`knowledge/data-overview.md:23-32`). The canonical (deduplicated) count from the pipeline dry run of 2026-06-10 is 2,457 objects, of which 2,451 were transcribed (`knowledge/data-overview.md:36`). The actually built catalogue carries 2,452 objects across five collections (`docs/catalog.json`, `meta`/`collections`; object array length 2,452). The README front matter therefore predates the fifth collection and was never updated (see History).

The five collections and their material are: Lebensdokumente (127 objects, 2,879 images; contracts, legal and office documents, notebooks), Werke (169 objects, 7,842 images; manuscripts, typescripts, galley proofs, the image-heaviest collection at 42% of all scans), Aufsatzablage (625 objects, 3,844 images; newspaper clippings and register sheets), Korrespondenzen (1,186 physical / 1,157 canonical, 4,154 images; handwritten letters), and Briefkonvolute SZ-AAL, internal name `autographen` (379 objects, 1,599 images; letter convolutes, added 2026-06-10) (`knowledge/data-overview.md:25-32,242-250`; `pipeline/config.py:29-50`). Languages by TEI analysis are German 95.6%, English 2.6%, French 1.5%, Italian and Spanish as trace (`knowledge/data-overview.md:56-62`; `README.md:32`). Image format is JPEG at median 4800 by 7234 px, roughly 1.3 MB per image (`knowledge/data-overview.md:38`). Hands, writing instruments (violet ink as Zweig's standard), and object types are catalogued per collection from the TEI (`knowledge/data-overview.md:117-127,206-212`).

Documented cost figures are sparse and cover only sub-experiments, never the full production run. Flash Lite input pricing is recorded as 0.25 USD per 1M tokens (`knowledge/journal.md:36`). The three-model ground-truth pipeline over 18 objects cost about 8 to 12 USD including the Flash consensus (`knowledge/verification-concept.md:203`). A planned but unexecuted prompt-ablation was estimated at roughly 90 API calls and under 3 USD (`knowledge/verification-concept.md:255`). Verification-by-vision via the Gemini API is priced at about 0.001 USD per page, while the Claude Code agent channel is booked at 0 USD (`knowledge/verification-concept.md:301`). Timing figures are equally local: a batch of 8 agent-verification objects takes about 3 minutes (`knowledge/verification-concept.md:395`), and manual reference transcription is estimated at 15 to 45 minutes per page (`knowledge/verification-concept.md:72`). No document records a total token count, cost, or wall-clock duration for transcribing the roughly 2,450-object corpus.

### The transcription setup

Prompting is organised as a layered stack assembled per object. Layer 1 is a shared system prompt defining role, diplomatic-transcription rules, the markup conventions, blank-page and bleed-through handling, and the mandatory JSON output schema (`pipeline/prompts/system.md:5-52`). It is passed to the model as `system_instruction`, separate from the content parts (`pipeline/transcribe.py:383`). Layer 2 is one of nine group prompts A to I (handwriting, typescript, form, short text, tabular, galley proof, convolute, newspaper clipping, correspondence), loaded at import (`pipeline/transcribe.py:41-51`; `pipeline/config.py:90-100`). Layer 3 is an optional per-object override under `pipeline/prompts/objects/{id}.md`; only one such file exists (`o_szd.1056`) (`pipeline/transcribe.py:56-61`; prompts tree). Layer 4 is a per-object context string derived from the TEI metadata (`resolve_context` in `pipeline/transcribe.py:154`). At call time the group prompt, the context, and a short transcribe instruction are concatenated into the user turn alongside the image parts (`pipeline/transcribe.py:429-437`). Group assignment is automatic from TEI object type via `resolve_group` (`knowledge/data-overview.md:274`).

The transcription model is `gemini-3.1-flash-lite-preview`, configurable via `HTR_MODEL` (`pipeline/config.py:25`); layout analysis uses `gemini-3-flash-preview` (`pipeline/config.py:26`). Temperature is 0.1 (`pipeline/transcribe.py:384`). The recorded rationale for Flash Lite is low cost, speed, a 1M-token context, multimodality, and the option of a cross-provider comparison (`knowledge/journal.md:35-37`). Objects with more than 20 images are chunked at 20 images per chunk and merged, with a sub-chunk retry path for failed chunks (`pipeline/config.py:74`; `pipeline/transcribe.py:445-577`). API calls carry exponential backoff on rate-limit and timeout errors (`pipeline/transcribe.py:377-396`).

Export for archival exchange runs in three paths, one more than the README's "two export formats" claim (`README.md:69`). Page-JSON v0.2 is the internal working format carrying OCR, layout, and Dublin-Core/MODS descriptive metadata (`schemas/page-json-v0.2.json`; `pipeline/export_page_json.py`). The archival target is a METS container with MODS (mapped from TEI) plus one PAGE XML 2019 file per page (`pipeline/export_mets.py`; `pipeline/export_pagexml.py`; `knowledge/page-xml-mets-architecture.md:107-114`). A third path exports Page-JSON to teiCrafter-loadable TEI deterministically, as a byte-for-byte Python port of a JavaScript reference converter with no LLM or API call (`pipeline/export_tei.py:1-20`). The TEI to MODS field mapping is tabulated in `knowledge/page-xml-mets-architecture.md:82-97`.

### Pipeline output per object

The primary result file is `results/{collection}/{object_id}_{model}.json` (`results/README.md:9`). Its top-level keys are `object_id`, `collection`, `group`, `model`, `metadata`, `context`, `result`, `quality_signals`, `review` (verified against `results/lebensdokumente/o_szd.100_gemini-3.1-flash-lite-preview.json`). `metadata` carries `title`, `language`, `images`. `result` carries `pages[]`, `confidence` (one of high/medium/low), `confidence_notes`. Each page carries `page`, `transcription`, `notes`, and a pipeline-assigned `type` (`content`/`blank`/`color_chart`) set by the quality-signal classifier (`pipeline/quality_signals.py:38-56,161-168`). On the first edit of a page, two further fields appear: `transcription_llm`, the immutable raw LLM stream set once, and `edit_history`, a list of `{original_transcription, edited_by, edited_at, source}` entries (`pipeline/serve.py:159-168`; verified in `results/aufsatzablage/o_szd.2213_gemini-3.1-flash-lite-preview.json`). The working `transcription` field always holds the current best text.

Secondary files per object are byproducts of the verification and export stages: `{id}_consensus.json` (model consensus), `{id}_gemini-3.1-pro.json` (second transcription), `{id}_layout.json` (VLM region detection), `{id}_page.json` (Page-JSON v0.2), a `{id}_page/` directory of PAGE XML, `{id}_mets.xml`, and `.tei.xml` exports (`results/README.md:9-15`). Only the primary file is read by the viewer builder (`results/README.md:30-32`).

### Editorial engagement recorded in the data

The degree of editorial engagement is recorded in the `review` block and in per-page `edit_history`. The stored `review.status` takes three values: `approved` and `gt_verified` (human-checked, treated as ground truth for CER), and `agent_verified` (Claude-vision agent checked the image against the text) (`knowledge/verification-concept.md:31-35`). An absent `review` block means unreviewed. Human reviews carry `status`, `edited_pages`, `reviewed_by`, `reviewed_at`; agent reviews additionally carry `agent_model`, `errors_found`, `estimated_accuracy` (`pipeline/serve.py:97-110`; `knowledge/verification-concept.md:383-393`). Correction provenance is distinguished in `edit_history.source` as `human` or `agent` (`pipeline/serve.py:166`; agent path in `pipeline/backfill_edit_history.py`).

The `needs_review` flag from the quality signals is explicitly not a status; it is a triage hint inside the unreviewed state (`knowledge/verification-concept.md:39`). In the display layer the stored statuses are collapsed to three via `isHumanChecked()`/`isAgentChecked()` (`docs/app.js:118-130`). The actual review coverage in the built catalogue is 19 `approved`, 85 `agent_verified`, and 2,348 with no review, with 324 objects flagged `needsReview` (computed from `docs/catalog.json`). Human plus agent review therefore covers about 104 of 2,452 objects.

Corrections flow back through a local server. The frontend edit and approve actions POST to `pipeline/serve.py`, which writes the change directly into the pipeline result JSON after copying a `.bak` backup, so the pipeline JSON is the single source of truth rather than browser storage (`pipeline/serve.py:112-119,184-191`; decision in `Plan.md:160`). The curated JSONs are then committed and pushed, and the next GitHub Pages deploy carries them into the public read-only proto-edition (`README.md:104-117`).

### Quality assessment without ground truth

Quality signals are text statistics computed after transcription with no further API call (`pipeline/quality_signals.py:142-274`; `knowledge/verification-concept.md:207-213`). Version 1.6 exposes seven fields but drives `needs_review` from only three: `page_length_anomaly`, `page_image_mismatch`, and `language_mismatch`; `duplicate_page_pairs` and `marker_density` remain informational, and DWR was removed in v1.5 (`pipeline/quality_signals.py:243-249,33-35`). Recorded precision against 62 agent-verified objects is 100% for page_image_mismatch and page_length_anomaly, 50% for language_mismatch, 0% for duplicate_pages (`knowledge/verification-concept.md:219-229`; `knowledge/evaluation-results.md:172-180`). The classifier first synchronises the page list to the image count, filling gaps as blanks via `_fill_missing_pages()` (`pipeline/quality_signals.py:92-139`). Envelope and address pages are exempted from the length anomaly since v1.6 because they are legitimately short (`pipeline/quality_signals.py:59-63,183-192`).

Two empirical accuracy figures exist. Corpus CER measured character-weighted against human corrections is 0.962% over 56 edited pages in 40 objects (114,000 reference characters), plus 16 human-checked objects with no edits counted as error-free by convention (`reports/cer-from-edits.md:1-5`). The CER baseline from 58 verified objects across all nine groups spans below 5% for print to about 10% for difficult handwriting and tables, with a full error typology (`knowledge/evaluation-results.md:28-35,60-72`). The recurring hard cases are systematic Fraktur long-s to f substitution, Kurrent letter confusions, and nonsense hallucination where the model invents real words instead of setting an uncertainty marker (`knowledge/evaluation-results.md:85-114`). The interface surfaces signals as a triage marker in the catalogue Status column and shows the detailed signals, consensus tab, and correction diff only in the object view (`knowledge/verification-concept.md:319-328`).

### The interface

The viewer is a static single-page app built from `docs/index.html`, `docs/app.js`, and `docs/app.css`, loading `catalog.json` and `data/{collection}.json` (`Plan.md:136`). Public read-only mode versus local editing mode is switched by hostname: `state.isLocal` is true for `localhost`, `127.0.0.1`, empty host, or `file:` protocol (`docs/app.js:236-237`), and edit controls render only when it is true (`docs/app.js:431,1561,1596`). The architectural claim is that the public site is a subset of the local site reached by disabling the editing controls, same code and same URL (`README.md:71-73,140`).

`pipeline/serve.py` serves `docs/` and exposes four local-only endpoints: `POST /api/approve`, `POST /api/edit`, `GET /api/status` (the frontend probe, absent on Pages), and `GET /api/git-status` (uncommitted count under `results/`) (`pipeline/serve.py:9-14,266-337`). It also serves local backup facsimiles for not-yet-ingested placeholder objects via a `/local-image/` route with path-traversal protection (`pipeline/serve.py:278-307`). Security measures are a DNS-rebinding Host-header check restricting to localhost and a CORS origin allowlist for localhost origins (`pipeline/serve.py:249-264,339-345`). Above the catalogue, a local-only Editorial Workspace dashboard shows recent `results/` commits via the GitHub API, an uncommitted indicator backed by `/api/git-status`, and copy-to-clipboard quick actions; a Project Transparency panel is shown both publicly and locally to make paper claims traceable (`README.md:85-101`). The curation-progress bar renders the five review states as a stacked bar and is described as following Vogeler's concentric edition model (2025) (`README.md:120-129`).

### Promptotyping presence

LLM-driven development is steered by a set of documents. `CLAUDE.md` at the root is the developer and AI guide (22 KB). `Plan.md` is a phased roadmap with an explicit decision log dated across 2026-04-01 to 2026-04-03 (`Plan.md:140-167`). The `knowledge/` vault holds thirteen Markdown documents indexed by `knowledge/index.md`, including data overview, annotation protocol, verification concept, evaluation results, the interchange-format and METS architecture specs, a security review, a stats-dashboard spec, dia-xai and teicrafter integration notes, and the research journal. The journal is the audit trail, a chronological log of 36 sessions from 2026-03-30 to 2026-06-21 (`knowledge/journal.md`; session count from headers). The repository organises knowledge inside the project rather than scattering it, and the frontend Transparency panel re-exposes the vault so reviewers can trace claims without cloning (`README.md:93-101`).

### Durability and reproducibility

The pipeline depends on the proprietary Google Gemini API for both transcription and layout (`pipeline/config.py:24-26`), and images are served from GAMS at the University of Graz or from a local backup, not committed to the repository (`README.md:45`; `pipeline/config.py:18-21`; `.gitignore:1-2`). The recorded mitigations against provider lock-in are the deterministic exports into open, provider-independent formats (PAGE XML 2019, METS/MODS, teiCrafter TEI), the last of which is explicitly LLM-free and byte-reproducible (`pipeline/export_tei.py:1-20`; `knowledge/page-xml-mets-architecture.md:107-114`), and the committing of all result JSONs to Git so the transcriptions survive independently of the API. A recorded reproducibility limit is VLM non-determinism: the same object yields different CER across runs, and temperature 0.1 is judged not deterministic enough (`knowledge/verification-concept.md:295`). The API key lives only in a gitignored `.env` (`.gitignore:4-5`; `knowledge/security.md:36`). Pinned dependencies are listed in `requirements.txt`.

### History and inconsistencies

The git log and journal show a development arc from March to June 2026 with heavy iteration on quality signals (v1.0 through v1.6), the review model, and the export formats. Several points are surprising or inconsistent with the surface documentation.

The journal is not strictly chronological toward the end, and session numbers are reused. A Session 24 appears twice and a Session 25 appears twice, and dated headers jump between April and June 2026 out of order (for example `knowledge/journal.md` headers show 2026-04-03 Session 24, then 2026-06-09 Session 25, then 2026-04-02 Session 20b). The audit trail is real but its numbering cannot be read as a clean sequence.

The README front matter is stale relative to the code and vault. It reports four collections, 2,107 objects, and 18,719 scans (`README.md:6,23`), a snapshot from before the fifth collection SZ-AAL was ingested on 2026-06-10 (`knowledge/data-overview.md:242-250`; `pipeline/config.py:34-37`). The canonical object count is documented as 2,457 and the built catalogue holds 2,452.

The deduplication logic is more involved than a headline count suggests. 34 Lebensdokumente objects are physically duplicated under `korrespondenzen/` in the backup, a doubling that originates in GAMS itself, and the pipeline canonicalises TEI-first with a backup tie-break governed by the order of `COLLECTIONS` (`knowledge/data-overview.md:34`; `pipeline/transcribe.py:105-123`). The Korrespondenzen TEI catalogues at convolute level and yields zero usable object PIDs, which is a granularity fact rather than a parser bug, so every Korrespondenzen object is canonicalised through the backup fallback (`knowledge/data-overview.md:77`; `pipeline/transcribe.py:83-95`).

Two planned steps were deliberately skipped or never built. The manual ground-truth pilot was skipped in favour of model consensus plus the GT pipeline (`Plan.md:64`; `knowledge/verification-concept.md:72`), and the prompt-effectiveness ablation, described as cheap, was never run (`knowledge/verification-concept.md:255,431`). A `consensus_corrected` category and a `group_text_density` signal were specified but never implemented (`knowledge/verification-concept.md:347`; `pipeline/quality_signals.py:227`).

A truncation defect is documented candidly: `run_sample_batch.py` defaulted `--max-images` to 5, capping objects to five images, after which `transcribe.py --all` skipped them as already existing; 97 objects were affected, and the chunking was not the cause (`knowledge/evaluation-results.md:150-154`).

The second model is not the one first recommended. Claude Sonnet was planned as model B for maximum provider diversity, but Gemini 3 Flash was implemented instead as cheaper and same-provider, with cross-provider diversity moved into the Claude judge and the agent verification (`Plan.md:147`; `knowledge/verification-concept.md:270`). Model version labels are mixed across the record: the README credits Opus 4.6 for building the project, stored agent reviews carry `agent_model` `claude-opus-4-6` (`pipeline/serve.py:104`; `results/aufsatzablage/o_szd.2213_...json`), while the 2026-06-10 SZ-AAL triage report used `claude-opus-4-8` (`knowledge/evaluation-results.md:184`).

The signal calibration is honestly presented as corpus-dependent. Precision validated on Lebensdokumente and Werke did not transfer to the letter convolutes, where short envelope address sides against long letter medians produced a wave of false positives, corrected in v1.6 (`knowledge/evaluation-results.md:182-197`; `knowledge/verification-concept.md:241`).
